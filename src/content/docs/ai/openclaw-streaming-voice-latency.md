**流式语音的首句延迟，分布在“什么时候提交、什么时候发出模型请求、什么时候转发、什么时候真正播放”四处。** 我们在一台边缘设备上接入 OpenClaw，保持核心源码、角色与工具能力、自定义 LLM 路径不变，把能前移的准备移到启动，把能重叠的工作并行，并修复了中转和 UI 中的等待。

这些修改消除了几处可复现的阻塞，仍未让所有对话稳定低于某个秒数。排查中反复出现的误判，是把“收到数据”当成“用户已经听见”，把尚未发出请求的时间算进模型耗时。

[![流式语音优化概览：及时提交、启动预热、逐段传输和跟随播放，沿麦克风到扬声器的路径定位等待。](/images/ai/openclaw-streaming-latency/overview.webp)](/images/ai/openclaw-streaming-latency/overview.webp)

下文数字来自 2026 年 10 月 23—26 日的设备日志与隔离实验。设备、业务和请求标识已脱敏；不同起止点的数据分开列出，不合成一个“优化百分比”。

## “hello hello”为什么仍然要等 7.4 秒

链路由本地 WebSocket 串起：麦克风 → 语音识别（ASR）→ 插件 → OpenClaw Agent → 后端中转 → 模型 → 语音合成（TTS）→ 浏览器播放。模型和 TTS 支持流式，并不代表中间每一层都及时交付。

早期文本探针已经出现过 2～3 秒收到音频的结果，真实反馈却仍是：“hello hello 还是很慢。”核对同一轮记录，从 UI 提交语音到播放器首次进入 `playing`，用了 **7,418 ms**。

[![一轮真实语音的等待分解：ASR 收尾 579 毫秒，请求前准备约 3686 毫秒，HTTP 发出至首个正文约 2463 毫秒，正文至起播 690 毫秒。](/images/ai/openclaw-streaming-latency/hello-timeline.svg)](/images/ai/openclaw-streaming-latency/hello-timeline.svg)

*这是一个慢样本，起点是 UI 提交，不是用户停止说话；VAD 判停的等待尚未包含。中间 HTTP 发出时点由日志耗时推算，分段值含近似量。*

最大的等待出现在 ASR 已有最终文字、模型请求却尚未发出的阶段。更容易误判的是：日志中的 `agent_run_start` 之后，距离真正发出 HTTP 请求仍有约 **2,338 ms**。把这个回调当成模型计时起点，就会把本机准备误算成网络或模型推理。

这次之后，测量边界被拆开：提交、ASR final、Agent run、HTTP 发出、上游响应头、首个有效正文、首段稳定文本、首个可解码音频帧、播放器 `playing`。空 SSE 事件不算正文，MP3 文件头不算可播放音频；`playing` 也只是浏览器开始播放的证据，声卡和扬声器还要另验。[MDN 对 playing 事件的定义](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/playing_event)

## 预热必须走过真正会冷掉的路径

最初的目标是把对话前约十余秒的准备挪到启动期。第一版通过插件调用原有回复分发入口，在 Agent 启动回调处取消，避免向真实模型发送请求。

这版确实缩短了一组隔离样本的请求前等待：未预热首轮从 dispatch 到 HTTP 请求为 **5,983 ms**，预热后首轮为 **1,837 ms**。但随后真实对话仍慢，说明这个取消点没有覆盖完整路径。

[![预热范围对比：早期在 Agent 启动回调取消，后续序列化、HTTP 与 SSE 仍未执行；修正版使用独立会话走本机响应并正常收尾，用户输入优先。](/images/ai/openclaw-streaming-latency/warmup.webp)](/images/ai/openclaw-streaming-latency/warmup.webp)

当时运行版本中的请求序列化 Worker 会在空闲后退出。只准备工具和上下文，或在 payload 回调中提前取消，都可能漏掉后面的序列化、HTTP、SSE 解析与回复收尾。预热日志显示成功，不等于下一轮经过的资源都还热着。

修正版借助插件的 Provider 扩展包裹原生流式函数：普通请求原样交给原函数；只有本进程登记的私有预热请求，才使用克隆的调用参数，转向**同进程的本机回环 HTTP 路由**。该路由返回固定 SSE，让原生处理链正常完成。真实用户的模型地址、凭据和请求参数不变，也没有给 OpenClaw 核心或全局 `fetch` 打补丁。

预热只准备本机请求链，不会提前运行云端模型。它还必须有明确的隔离与退出条件：

- 使用随机独立会话和一次性标记，不把固定测试文本写入用户主会话。
- 本机路由校验来源、标记和请求体大小；私有调用替换真实凭据。
- 用户输入优先取消预热；清理让出前台数据库写入机会。
- 用宿主提供的生命周期接口回收临时记录。清理失败就停止维护，不能继续堆积会话。

这里踩过一个具体坑：配置了“不持久化下一条消息”，该入口仍留下了临时记录；普通删除会话又未清完相关数据。只有核对临时会话与转写记录实际归零，才算清理完成。

修正版的原生文本链路隔离验证如下。每行是一轮观察，包含启动预热与空闲维护，不含 ASR、TTS 和扬声器：

| 场景 | 输入到 HTTP 请求 | 输入到首段正文 |
| --- | ---: | ---: |
| 启动预热后第一句 | 1,380 ms | 3,693 ms |
| 紧接第二句 | 1,483 ms | 3,232 ms |
| 空闲 120 秒后第一句 | 691 ms | 2,496 ms |

这一组启动准备为 13,489 ms，预热期间真实模型请求为 0，主会话保持不变，临时会话完成回收；受限的真实工具读取也通过。**成本被前移，并没有消失。** 它增加了启动时间和后台维护工作，而且只对当时验证过的版本与 Provider 路径开放，不能当成所有 OpenClaw 部署通用的开关。

## 把“支持流式”变成“确实逐段到达”

本机准备缩短后，还要确认数据没有被中间层攒住。我们用相同模型和固定短文请求，对比公网路径与直达同一后端的诊断路径；生产模型地址保持不变。

| 路径与状态 | SSE 首包 | 首个正文 | 响应结束 |
| --- | ---: | ---: | ---: |
| 修改前，经公网 | 3,271 ms | 3,271 ms | 3,272 ms |
| 修改前，直达后端 | 528 ms | 1,692 ms | 3,600 ms |
| 修改后，经公网 | 502 ms | 2,253 ms | 4,123 ms |

第一行的关键是：多个块几乎在最后 1 ms 内集中送达。直达后端时正文持续到达，说明不能只检查业务代码有没有逐块写出。

后端为 SSE 响应增加以下头部后，该轮公网复测恢复了连续到达：

```http
Cache-Control: no-store, no-transform
X-Accel-Buffering: no
```

`no-store` 和 `no-transform` 分别约束缓存存储与内容转换；`X-Accel-Buffering` 是否生效取决于中间层。这些头不是适用于所有网络的“关闭缓冲万能药”。我们没有确认入口的具体产品，也没有把不同轮模型生成的时间差全部算作修复收益。[Cache-Control 语义](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control)、[SSE 服务端发送示例](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)

[![文本、连接与播放重叠：中转逐段发送，模型生成时准备 TTS 连接，稳定短句开始合成，可播放音频到达后起播。](/images/ai/openclaw-streaming-latency/streaming.webp)](/images/ai/openclaw-streaming-latency/streaming.webp)

TTS 也存在可前移的等待。一轮冷连接样本中，从 TTS 请求到首包用了 **2,172 ms**，复用连接的一轮为 **184 ms**。改动是在输入提交或文本派发时，并行准备既有 TTS 中转链路的连接，让建连与模型生成重叠；准备失败不阻塞 LLM，不为预连接发送合成文本。

修改后观察到的 TTS 请求至首包为约 **185～309 ms**；一次冷连接准备耗时 1,207 ms，但在首句生成前已经完成。这是连接工作被隐藏在并行阶段内，不是模型本身快了 1.2 秒。

模型输出按稳定短句送入 TTS，浏览器收到小音频块就及时追加到播放缓冲，不等整段回复生成完。但追加数据不等于能够解码：实际抓到的第一包只有 **44 字节**，只是 MP3 文件头。因此探针继续检查完整音频帧，UI 继续记录 `playing`，没有用“首包很快”替代播放验证。

## 不再无限等 VAD，也不让字幕抢跑

输出通了，输入端仍可能拖延。现场的另一类问题是：用户说完话，环境还有噪声，VAD 仍判断语音段未结束，ASR 文字却已经不再变化。VAD 判断声音活动，并不能独立回答“这句话是否应当提交”。

我们增加了一个兜底：**已有非空识别文字，连续 1 秒没有有效内容变化，就主动提交当前音频段。** 新词或改词重新计时；重复文本、空白、大小写和标点变化不延长计时。没有文字时不触发，ASR 错误时停止这条定时器。

提交后仍等待 ASR Finalize 的最终结果，没有把临时字幕直接当作 LLM 输入。自动提交与正常 VAD 结束共用入口，同一段只提交一次。插件完成该段的收尾后返回带请求标识的确认，UI 用它隔离上一段迟到结果；确认只代表该段处理结束，空结果或失败也可能得到确认。

这条规则缩短的是**识别停止更新后的等待**，不是承诺 1 秒内回复。识别服务卡顿、长停顿、慢速说话仍可能导致过早切段，需要真实录音回归；旧插件未声明确认能力时，UI 保留原 VAD 提交方式。

[![输入与字幕的边界：已有文字停止有效更新一秒后提交音频并等待最终识别；输出字幕按真实播放位置推进，暂停时停止走字。](/images/ai/openclaw-streaming-latency/turn-display.webp)](/images/ai/openclaw-streaming-latency/turn-display.webp)

字幕侧选择了明确的体验：**回复文字与对应语音同时出现。** 文本属于哪一段音频，由音频开始事件携带；等对应播放器进入 `playing` 才展示，避免第一段播失败后错用下一段的字幕。

长回复按播放器 `currentTime` 推进可见窗口，保留上一行与当前行。网络缓冲导致播放停住时，字幕也停住；有词级时间戳就按时间戳对齐，没有时只按时长估算，不声称逐字准确。

恢复 Agent 状态显示时，又要处理文字与状态的优先级：ASR 和 AI 文字在最近一次有效更新后至少保留 **1.5 秒**，之后允许当前 Thinking 或工具状态接替；无更新最多保留 **7 秒**。新一轮真实 ASR 或回复可以直接替换旧内容，持续播放的进度会续期，长音频不会播到第 7 秒就丢失字幕。状态与文字使用独立身份，迟到的旧状态不能把当前内容盖住。

这些行为已通过实际 Vue 组件的设备浏览器回放，包括暂停不走字和状态定时接替；回放输入是模拟事件，仍需与真实麦克风对话区分。

## 下载压力与模型长尾，要分开归因

边缘设备同时播放角色视频、下载资源和处理语音。重复缓存和集中写入会拖慢前台，所以下载改为受限并发、限速和背压传输；通话时让出资源，旧视频读取不再顺带重写 Blob。目标是前台仍能响应，而不只是下载更快。

旧实现的一轮约 61 秒压力试验触发保护停止，健康检查超时 10 次；修正版隔离试验持续约 279 秒、完成 34 个文件，健康检查无超时，最大约 116 ms。两轮工作量与时长不同，只能说明修正版在这组负载下保持了响应，不能据此计算统一提速倍数。后续约 383 秒的真实业务下载仍有一次超时，同期出现较长的预热数据库清理，因此也不能宣称资源争用全部消失。

反过来，设备健康也不等于回复一定快。一次下载压力期间的文本探针，客户端约 **7.55 秒**才收到首音频包。按时间、顺序、模型和输出长度对照后端日志，上游响应头等待为 **5.34 秒**；鉴权、DNS、TCP、TLS 记录均为 0 ms，连接已复用；TTS 首包约 177 ms。同期设备健康检查正常，磁盘采样也不支持连续数秒的本地 IO 堵塞。

这组关联当时没有统一的端到端 request ID。它支持“主要等待在上游响应阶段”，尚不能细分服务端排队、推理或返回链路耗时；继续改播放器缓冲也解决不了这段等待。

还存在另一类约 8 秒的样本：上游等待不足 1 秒，请求抵达后端业务入口前却有额外延迟。现有日志无法细分设备准备、传输与入口鉴权，后续也未稳定复现。两类长尾不能混成同一个根因。

## 验收要保留慢样本

这轮最明确的成果，是完整本机预热、SSE 连续转发、TTS 提前建连、ASR 无更新提交，以及按播放位置显示字幕。它们分别修复了可观察的等待或状态问题；**“任何时候首句都一样快”仍未达成。**

接下来的验收应覆盖启动后的第一轮、连续对话、空闲后的第一轮，以及下载并行时的真实语音。固定短问候适合定位链路，还要补自然长句、停顿、背景噪声和打断；被打断的样本单列，不当成功样本，也不悄悄丢掉超时。

下一步优先贯通同一轮请求标识，补齐后端受理、上游首个有效文本和下游转发的时间；同时测量预热清理的数据库竞争。角色、工具、历史上下文是否确有重复，可另做审计，但不能靠删能力、换模型或把“正在思考”当作首句回复，让数字看起来更好。
