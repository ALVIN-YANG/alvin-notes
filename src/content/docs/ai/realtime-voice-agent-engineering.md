**实时语音 Agent 要同时管住回应时间、打断和实际动作状态。** ASR 把声音转成文字，模型与工具处理请求，TTS 再合成声音。支持流式协议只是前提，真正影响体验的是：识别何时提交、请求前准备是否完成、中间层是否攒包、TTS 是否等全文、播放器何时真的能出声。

每一轮用同一个 turn ID 串起识别、生成、播放和工具结果。用户插话时，停止扬声器还不够，旧生成、待播音频和后续动作也要取消或隔离。已经完成的外部操作不会因打断自动撤销。

## 1. 一轮语音要分段计时，不要只记模型耗时

```text
采集、降噪、回声消除
  → VAD 与轮次判断
  → ASR 最终文字
  → 请求前准备
  → 模型与工具
  → TTS 合成与传输
  → 播放缓冲与扬声器
```

| 阶段 | 应该测什么 |
| --- | --- |
| 用户停顿到判定轮次结束 | endpointing latency |
| 最后一帧到 ASR final | ASR finalize latency |
| 文本到模型首个 token | model time-to-first-token |
| 外部操作 | tool latency |
| 文本到首个可播放音频 | TTS time-to-first-audio 与解码验证 |
| 网络与播放 | 传输、jitter buffer、播放器 `playing`、实际听感 |

这些阶段可以重叠，因此不能把各段预算简单相加当成实际等待。应该按时间戳和 turn ID 找到最长的一段，再优化那一段。

`playing` 只证明浏览器开始播放，不证明声卡和扬声器符合听感；SSE 空事件不算正文，MP3 文件头也不算可播放音频。[MDN playing 事件](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/playing_event)

## 2. “有人说话”和“一轮说完”是两个判断

VAD（语音活动检测）判断有没有声音，Turn Detection 判断这一轮是否结束。停顿阈值短会抢话，阈值长会迟迟不回应。可以结合 VAD、ASR partial、标点与语义完整性和最大等待时间，按键或显式结束作兜底。

| ASR 结果 | 可以做什么 | 不能据此做什么 |
| --- | --- | --- |
| partial，仍可能修订 | 实时字幕、预热意图、准备上下文、辅助判断仍在说话 | 直接执行退款、取消等副作用 |
| final 或稳定轮次 | 校验参数与权限，满足条件后执行 | 把识别成功当成动作成功 |

OpenClaw 的一个现场问题是：环境里仍有噪声，VAD 没结束，但 ASR 文字早就不变了。兜底规则是：已有非空识别文字，连续 1 秒没有有效内容变化，就主动提交当前音频段。出现新词或改词重新计时，重复文本、空白和标点变化不延长；没有文字时不触发，ASR 出错时取消定时器。

**主动提交音频段后，仍要等 ASR Finalize 的最终结果，不把临时字幕直接交给 LLM。** 自动提交与正常 VAD 结束走同一入口，同一段只提交一次。这个 1 秒只是当前设备的试验参数，慢速说话和长停顿需要另测。

## 3. 打断必须贯穿生成、播放和工具

用户播放时插话，处理顺序是：检测语音 → 降低或停止播放 → 清掉未播缓冲 → 取消当前 TTS → 尽可能取消模型生成 → 记录实际已播放位置 → 新一轮送入 ASR。

```text
SPEAKING → INTERRUPTING → LISTENING
```

对话状态可以明确保存为：

```text
IDLE / CONNECTING / LISTENING / THINKING
CALLING_TOOL / SPEAKING / INTERRUPTING / RECONNECTING / ERROR
```

UI、音频和服务端按同一组状态及 session/version 更新。迟到事件用轮次和序号隔离：

```json
{
  "session_id": "voice_123",
  "turn_id": 18,
  "event": "tts.audio.delta",
  "sequence": 42
}
```

进入 turn 19 后，turn 18 的音频不能继续播放。旧回答也不能按全文写进下一轮上下文，因为用户只听到了其中一段。

工具已完成的外部操作不会随打断恢复；正在执行且结果未知的动作要查询状态，新动作停止调度。需要补偿时按业务规则执行，不能用“用户打断了”代替回滚。

## 4. 实测拆解：7.4 秒不是都花在模型上

以下数据来自 OpenClaw 2026.10.3 的设备日志与隔离实验，只代表该集成环境，不是框架性能排名。

某轮真实语音从 UI 提交到播放器 `playing` 共 7,418 ms，还不包括提交前的 VAD 等待。

![一轮真实语音的等待分解：ASR 收尾、请求前准备、HTTP 与播放](/images/ai/openclaw-streaming-latency/hello-timeline.svg)

| 阶段 | 观察到的时间 |
| --- | ---: |
| ASR 收尾 | 579 ms |
| 请求前准备 | 约 3,686 ms |
| HTTP 发出至首个正文 | 约 2,463 ms |
| 正文至起播 | 690 ms |

最长的是请求前准备。日志里的 `agent_run_start` 也不等于 HTTP 已发出，该回调后还有序列化等工作。若只从回调开始给模型计时，会把本机准备也算进去。

### 预热必须走完整请求链

第一版预热只准备工具和上下文，随后取消，没经过请求序列化、HTTP、SSE 解析和回复收尾。隔离样本看似有效，真实对话仍慢，因为后续路径没有被预热。

修正版用插件 Provider 扩展包住原生流式函数：普通用户请求原样执行；只有本进程登记的私有预热请求，才转向同进程的回环 HTTP 路由。该路由返回固定 SSE，让原生处理链完整跑一遍。真实模型地址、凭据和参数不变，真实模型请求数为零，也没有修改 OpenClaw 核心或全局 `fetch`。

![早期预热只走一部分，修正版用独立会话走完整本机请求链](/images/ai/openclaw-streaming-latency/warmup.webp)

| 场景 | 输入到 HTTP 请求 | 输入到首段正文 |
| --- | ---: | ---: |
| 启动预热后第一句 | 1,380 ms | 3,693 ms |
| 紧接第二句 | 1,483 ms | 3,232 ms |
| 空闲 120 秒后第一句 | 691 ms | 2,496 ms |

这组测试把 13,489 ms 的准备移到启动时，代价是启动变长和空闲维护。预热使用独立会话与一次性标记，用户输入到达必须让路；临时记录清理失败要停止后续预热。换 OpenClaw 版本或 Provider 后需重新验证。

### 中间层可能把流式数据攒到最后

相同模型和固定短文请求下，修改前公网路径的 SSE 首包、首个正文和响应结束几乎挤在一起；直达后端时正文持续到达。后端给 SSE 响应增加以下头之后，该轮公网复测恢复连续到达：

```http
Cache-Control: no-store, no-transform
X-Accel-Buffering: no
```

这不是“关缓冲万能药”。`X-Accel-Buffering` 是否生效取决于中间层，不同轮次的模型生成差也不能全算成修复收益。

| 路径与状态 | SSE 首包 | 首个正文 | 响应结束 |
| --- | ---: | ---: | ---: |
| 修改前，经公网 | 3,271 ms | 3,271 ms | 3,272 ms |
| 修改前，直达后端 | 528 ms | 1,692 ms | 3,600 ms |
| 修改后，经公网 | 502 ms | 2,253 ms | 4,123 ms |

### TTS 建连与模型生成重叠

一轮冷连接样本中，TTS 请求到首包 2,172 ms，复用连接的一轮为 184 ms。两轮差额不能全归给建连，但连接本就可以提前准备。

改动是在输入提交或文本派发时并行准备既有 TTS 中转链路：建连与模型生成重叠，失败不阻塞 LLM，也不为预连接发送合成文本。修改后观察到 TTS 请求至首包约 185～309 ms。

![模型生成时准备 TTS 连接，稳定短句开始合成，音频到达后起播](/images/ai/openclaw-streaming-latency/streaming.webp)

模型输出按稳定短句送入 TTS，浏览器收到音频块就追加缓冲，不等整段回复完成。仍要验证完整音频帧和实际 `playing`，不能用“首包很快”代替播放验收。

## 5. 字幕、协议与恢复分别处理

字幕跟随真实播放位置：回复文字属于哪段音频，由音频开始事件带来；对应播放器进入 `playing` 后才展示，长回复按 `currentTime` 推进。网络缓冲卡住时字幕也停，避免文字已经说完、音频还在后面。

![输出字幕按真实播放位置推进，暂停时停止走字](/images/ai/openclaw-streaming-latency/turn-display.webp)

有词级时间戳就按时间戳对齐，没有就按时长估算，不能声称逐字准确。状态和文字分开记录，迟到的旧状态不能盖住当前回复。

| 链路 | 常见选择 | 恢复边界 |
| --- | --- | --- |
| 双向音频 | WebRTC | 处理媒体、拥塞与抖动，不替代业务状态机 |
| 字幕、turn 与 UI 事件 | WebSocket；单向推送可用 SSE | 与音频分别恢复，不能因重连丢弃旧轮次 |
| 设备命令与状态 | MQTT | 命令包含设备 ID、版本、有效期和幂等 ID |
| 内部服务调用 | HTTP / gRPC | 独立处理鉴权、超时与未知结果 |

恢复使用稳定 session ID、递增 turn/sequence、已确认游标和服务端 TTL，并明确本次是 resume 还是 restart。无法安全续传时，让用户重说刚才一句，不能偷偷拼接缺帧音频。

## 6. 音频接入、权限和资源竞争

浏览器先拿到麦克风，再排查模型或网络：

```javascript
if (!window.isSecureContext) {
  throw new Error("麦克风需要 HTTPS 或 localhost 安全上下文");
}

const stream = await navigator.mediaDevices.getUserMedia({
  audio: {
    echoCancellation: true,
    noiseSuppression: true,
    autoGainControl: true
  }
});
```

这些约束是请求，实际设置取决于浏览器和设备。还要确认采样率、声道、PCM/Opus、帧长、蓝牙切换和扬声器回采。[W3C Media Capture](https://www.w3.org/TR/mediacapture-streams/)

麦克风开启状态要可见，录音、转写和长期保存分别告知并取得相应授权。声纹不能作为唯一身份依据，高风险动作仍需参数确认。外部音频与转写记录按不可信输入处理，不能让音频指令自动扩权。

边缘设备同时下载角色视频、处理语音和运行清理任务时，要限制并发、速度和背压，通话期间让出资源。此次修正版在隔离负载下完成 34 个文件且健康检查未超时，但真实业务下载仍出现过超时，不能宣称资源争用已经消失。

首句长尾也不能统一归因。一次下载压力期间，上游响应头等待 5.34 秒，TTS 首包约 177 ms，说明主要等待在上游响应阶段；另一类约 8 秒样本，上游等待不足 1 秒，空档发生在请求抵达后端业务入口之前。没有统一 request ID 时，不能把它们写成同一个根因。

## 7. 推荐实施与验收顺序

1. **先记录时间。** 从用户说完测到实际起播，拆开识别、准备、模型、中转、TTS 和播放，先找最长段。
2. **先让已有结果尽快出去。** 检查中间层攒包、TTS 等全文、播放器等全部音频，再做复杂预热。
3. **提前做可复用准备。** 启动时准备完整本机请求链，模型生成时准备 TTS 连接；用户输入一来，后台准备必须让路。
4. **先把半双工做稳。** 轮次、turn ID、工具回执和播放状态统一后，再增加打断和全双工。
5. **按真实环境验收。** 安静室内、电视或多人说话、蓝牙、弱网切网、快速插话、长停顿，以及方言、数字、英文缩写都要覆盖。

核心指标包括首次连接成功率、首音频 P50/P95、业务实体识别准确率、打断生效时间、旧音频泄漏时长、重连恢复率、工具成功率和错误回执率。启动后说一句、连续说几句、空闲后再说、同时下载资源再说，都要测试。

目前这些 OpenClaw 改动已经处理了明确的等待点，但首句仍有长尾，不能宣称根治。后续仍需把设备与后端同一轮的请求标识串起来，并保留慢样本、超时和失败率一起评估。[脱敏观察数据](/images/ai/openclaw-streaming-latency/observations.json)可复核文中数值，但不能替代原始日志审计。
