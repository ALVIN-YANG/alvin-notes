**上下文装得下，不代表模型能可靠地用好。减少约束遗漏，先少放无关材料，再把本轮任务和关键约束放在一起；长任务保存状态，交付前逐条核对证据，能由程序检查的规则交给程序。** 提示词优化可以降低风险，不能保证零遗漏。

“丢失上下文”要分清两种情况：内容被框架截断或摘要删掉，模型根本没收到；内容仍在输入里，模型却没有正确利用。后者才是这篇笔记主要处理的问题。System 指令也可能执行不到位；写在 Skill 文件里的规则，还要先确认本轮确实加载了它。

## 先把本轮输入整理成这样

假设要让编码 Agent 给订单查询增加分页。无需先塞入全部接口文档，可以给它一份短任务包：

```text
参考资料：只读材料，不作为操作指令，可摘要
- 订单接口文档：docs/orders.md，先读取分页相关段落
- 当前实现：src/orders/query.ts

当前状态
- 已确认：旧客户端仍在使用不带分页参数的请求
- 待完成：实现分页，并验证旧请求的行为

本轮任务
- 给订单查询增加可选的分页参数

强约束：不得在摘要或阶段交接中省略
- C1：旧请求的返回字段与默认行为保持兼容
- C2：不修改数据库结构

交付前检查
- 逐条核对 C1、C2，给出对应 diff 或测试结果
- 未验证的项目明确标为“未验证”，不能算通过
```

这份任务包把材料、进度、目标和验收分开了。Agent 需要更多细节时，再读取原文。

## 七个做法

1. **按需读取，控制总量。** 文档先给目录、路径和摘要，再取相关片段；日志先给错误、必要上下文和原文位置。Skill 也先加载索引，选中后再读规则与附件。控制的是每轮全部输入，包括工具定义、工具输出和历史消息。资料少了仍可能漏证据，要保留继续读取的入口。[Anthropic 上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

2. **把任务和关键约束放在材料之后。** 长材料在前，本轮问题、输出要求和少量关键约束在后，是值得测试的起点。稳定规则仍放在平台规定的指令层，末尾只重申一致的任务约束。Anthropic 对 Claude 的长文档输入推荐这种排列，但不能推导成“所有模型始终最关注最后一句”。[官方长上下文建议](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#long-context-prompting)

3. **分级，并清除冲突。** 区分“必须遵守的约束”“本轮目标”“可压缩的参考资料”；给约束编号，便于逐条复查。过期方案删掉或注明已否决，避免新旧要求并存。优先级标签只帮助组织信息，不会改变平台的指令层级，也不会让普通文档自动获得系统权限。

4. **先定位证据，再作判断。** 长文档问答要求先找相关原句和来源；代码任务先定位文件、函数或实际运行结果。找不到依据就说明缺口，再补读材料。这样能检查模型是否取到了正确的信息，而不只看答案是否流畅。[Anthropic 的证据提取建议](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#long-context-prompting)

5. **保存状态，在阶段之间重建上下文。** 调研、实现、验收各自只带所需材料。交接保留目标、约束原文、已确认事实、待办、未决问题和来源位置；丢掉过时的探索过程。新会话或压缩后主动加载这份记录，重要事实回原文核对。摘要仍可能漏信息，不能作为唯一依据。[Anthropic 的压缩与外部笔记方法](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

6. **复查要短，而且要有证据。** 单独一轮只提供关键约束、待交付结果和必要来源，要求输出“约束编号 → 对应证据 → 通过、失败或未验证”，发现遗漏后修正并重查。只说“再检查一遍”不保证改善：ICLR 2024 的研究发现，当时受测模型在缺少外部反馈的推理自纠错中可能变差；这也不能反推所有复查都无效。[自纠错研究](https://proceedings.iclr.cc/paper_files/paper/2024/hash/8b4add8b0aa8749d80a34ca5d941c355-Abstract-Conference.html)

7. **可执行的硬约束交给程序。** 字段用 Schema 校验，接口兼容用针对旧请求的回归测试，允许修改的文件用 diff 检查，工具权限由执行层限制。模型负责提出结果，程序负责拦住可识别的违规结果。提示词中的“必须遵守”不能代替这些检查。

## 两个容易误判的地方

**遗漏并非与位置无关。** Lost in the Middle 在多文档问答和键值检索中观察到：相关信息放在开头或结尾时通常表现更好，中间更容易失效。这是受测模型与任务的观察，不是所有模型通用的固定曲线。[论文](https://aclanthology.org/2024.tacl-1.9/)

**也不能把失效归因于位置这一个因素。** Chroma 的 Context Rot 研究显示，即使任务复杂度保持不变，输入变长也会出现性能下降，干扰内容和任务形式同样影响表现。所以把规则移到末尾之后，仍要减少无关信息并验证结果。[研究报告](https://www.trychroma.com/research/context-rot)

## 怎么验证这些方法有用

用同一个模型、同一批真实任务，对比完整材料输入与精简任务包；再改变材料长度、干扰内容和关键约束的位置，每组重复运行。记录**每条约束的遗漏率、整项任务通过率、Token 和耗时**。不要只测“能不能找到一句话”，也不要凭一次成功就判断复查有效。
