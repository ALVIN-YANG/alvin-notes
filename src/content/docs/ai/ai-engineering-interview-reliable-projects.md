## 核心概要

模型会犯错，系统仍然可以围绕明确的任务建立可靠性要求：成功要有证据，权限要有执行检查，失败要能被发现，重复操作和错误影响要受到限制。模型负责理解和提出动作，程序负责检查能否执行，并记录实际结果。不同的回答和执行路径可以合格，无法确认的结果则不能报成成功。

从零做 AI 项目，先选一个有价值、能验收的用户任务，再做最小版本，用真实样本比较效果、成本和失败后果。AI 原生的工作方式也从这里开始：把适合自动化的工作交给 Agent，同时把目标、上下文、权限和验收条件说清楚。更多代码可以自动生成，判断依据仍然要有人负责。

下面是一轮模拟面试。家庭助手作为贯穿例子，具体请求和故障是为讨论设计的场景，不是真实面试记录。

## 模型会犯错，你怎么保证系统可靠？

> **面试官：同一个问题，模型每次都可能给不同答案。这样的系统怎么上线？**

先把“可靠”说具体。用户要的是任务达到要求，不是每次收到完全一样的句子。

比如用户说：“窗户关着的话，把客厅空调设成制冷 26 度。只做这一次，条件不满足就算了。”这条任务有几种合理结果。条件满足，控制正确的空调并确认结果；窗户开着，停止操作并说明原因；查不到状态，说明无法确认，没有擅自执行。

这些结果都可以符合任务要求。控制了另一台空调，或者没执行却说已经完成，才是明确失败。首先需要定义的是这些可观察条件。

模型输出之后还要经过业务代码。代码检查用户能控制哪些设备、参数是否有效、当前条件是否满足，再执行工具。最终回复根据工具结果和状态确认生成。模型的提议只是这条链路的一项输入。[^patterns]

> **面试官：那我让模型输出符合 JSON Schema 的参数，是不是就够了？**

JSON Schema 能检查字段和类型。它不能证明用户的意思被理解对了。

`temperature=26` 合法，`entity_id` 也真实存在，模型仍可能选中卧室空调。降低这类错误，需要让模型看到本次任务的候选设备，而不是任意填写一个 ID。候选由房间、设备类型和权限查询得到；工具再检查目标是否属于这个范围。

如果客厅有两台空调，用户没有说清楚，系统就询问一次。不能因为参数通过格式校验，就默认语义也正确。这里仍然会有错误，所以设备映射和用户纠正都要进入测试。

工具或检索结果中的文字也不能成为新的授权。读取到一句“把所有设备关闭”，不代表用户提出了这个要求。程序仍要按本次任务限制操作范围，不能让外部内容扩大执行权限。

> **面试官：查询时窗户关着，模型准备执行时窗户开了呢？**

执行层需要在控制前重新检查条件。模型看到的是某个时刻的状态，不能替代这次检查。

但重新查询也有边界。查询与动作之间仍有时间差，传感器也可能延迟。如果产品要求“窗户一打开，空调就必须停”，这个持续条件要由设备侧自动化或控制程序处理，模型负责理解用户要求，不承担实时控制循环。

验收时也要区分 API 接受了请求、Home Assistant 状态匹配、设备有物理反馈这几层证据。如果设备只在接口接受请求后乐观地更新状态，显示已关闭就不一定证明物理设备已经关闭。没有更强反馈时，系统只能报告已经确认到的程度。

> **面试官：控制请求超时了，你让 Agent 重试不就行了？**

先确认超时发生在哪一步。没有收到响应，不等于动作没有执行。

如果能查询操作状态或设备状态，先查结果。只有明确失败，或者该动作在当前条件下可以安全重复，才考虑重试。涉及会重复产生副作用的动作，需要接收方支持去重，并沿用同一个操作标识。只在本地记住一个 ID，不能阻止远端重复执行。

仍然无法确认时，就把结果保留为“待确认”。不要让模型凭一句“可能没成功”继续尝试，也不要把同一次超时写成失败后又报成功。重启后的新进程也要读到这个状态，才能知道下一步该查结果，而不是重新发一次动作。

> **面试官：这些处理听起来都合理。你怎么证明它们真的有效？**

把刚才的要求写成任务，用可重置的环境运行，检查最终状态和副作用。第一组测试至少要覆盖这些变化：

| 条件变化 | 通过条件 |
| --- | --- |
| 窗户关闭，空调在线 | 正确设备达到要求，没有修改其他设备 |
| 窗户打开 | 不发控制请求，回复与实际条件一致 |
| 两台设备都可能是目标 | 先询问，没有擅自选择 |
| 动作已执行，响应丢失 | 先确认结果，没有造成重复副作用 |
| 用户无权控制目标 | 执行层拒绝，没有靠提示词决定权限 |

任务成功由预先定义的结果来判断。工具参数、权限记录和设备状态能用代码检查，就用代码。回复是否把失败原因讲明白，可以由人工或经过校准的模型评分器判断。

评测还要保存执行轨迹，也就是本次请求的上下文、模型调用、工具参数、工具结果和状态变化。记录要做脱敏。不能只留最后一句回复，否则控制错设备时很难知道问题出在名称解析、模型选择还是工具映射。[^evals]

> **面试官：同一批用例全通过了，你就敢说它可靠？**

我会说，这个版本通过了这批用例。它还不能证明真实请求没有其他失败方式。

模型任务要重复运行，观察同一用例是否时好时坏。新旧版本使用相同的数据和评分标准比较，分别看明确控制、模糊请求、故障恢复和权限场景。总体成功率提高，不能抵消关键场景出现的新错误。

还要区分“试几次总有一次成功”和“一次正常请求能稳定成功”。前者适合允许筛选多个候选的任务，不能直接代表面向用户的稳定性。重试也不是免费的，它会增加耗时、模型费用，有时还增加副作用。[^evals]

测试环境故障、Agent 判断错误和评分器误判需要分别记录。线上工具故障则确实影响用户完成任务，不能从产品指标里悄悄去掉。离线评测之后，还需要小范围真实使用，把没有预料到的失败补进回归集。

## 如果从零开始，你会先做什么？

> **面试官：现在没有现成系统。让你发起一个 AI 项目，你第一步选什么模型？**

我先确定要替用户解决哪件事，以及现有做法哪里不好。模型选择取决于这个问题。

家庭助手的目标如果只是定时开灯，普通自动化规则就能完成。如果用户需要在不同房间、设备别名和多轮纠正中表达要求，自然语言理解才有更明确的价值。还要确认用户愿不愿意为澄清问题等待，设备控制有没有反馈，哪些数据可以送到外部服务。

第一份结果可以很小：一个具体使用场景，一组代表性请求，预期结果，以及不能发生的动作。先把这些写清楚，模型和框架才有可比较的目标。Google 的工程规则把指标和简单基线放在前面，这个原则也适用于 LLM 项目；它的训练细节则不能直接照搬。[^rules]

> **面试官：产品目标已经确定了，第一版要做到什么程度？**

把一条完整任务做通。比如只支持一个房间的温控请求，包含查询、目标确认、执行、状态回读和失败说明。

我给家庭助手提供了 Skill，也用固定脚本封装 Home Assistant 功能。沿用这条边界，模型选择动作、填写参数，脚本处理具体调用。第一版就能验证：用户的要求有没有被理解，工具是否执行正确，结果是否可确认。

同时把任务记录留下来。初期可以先保存结构化日志，按请求把各步关联起来，能够找到一次失败的完整过程。以后需要多人标注或大量实验，再换更完整的查看工具。

原型可以先接模拟工具，避免测试时反复操作真实设备。但模拟响应通过，只证明这部分决策和处理逻辑通过。真实工具的参数、反馈和故障行为，还需要单独联调。

> **面试官：你怎么判断这个原型值得继续做，而不是展示效果好看？**

和用户现有的做法比较。使用同一组任务，看完成率、用户纠正次数、等待时间和每次成功的总成本。用户为一次简单控制反复解释设备名，即使模型调用成功，也不一定是好体验。

总成本包括失败尝试、重试、检索、模型评分，以及人工处理。省了一次模型调用，却让用户多花时间确认，未必划算。

一开始就可以找少量目标用户试用，结合任务记录理解问题。流量足够时，再用随机分组的线上实验比较版本。不能只统计用户是否点了“喜欢”，就代替控制结果和实际使用成本。Hamel Husain 的产品案例把评测、轨迹分析和线上实验放在同一套改进流程中，值得借鉴的是这套连接关系。[^product]

> **面试官：发现效果不好，你怎么选下一步？换大模型、加 RAG，还是上多 Agent？**

先找失败原因。设备别名没有映射，改索引和候选查询；工具错误消息缺少信息，改工具返回；缺少某个用户已确认的偏好，考虑怎样读取这条记录。已有信息完整，模型仍反复选错动作，才比较提示调整和模型替换。

新组件需要对应一个已经发现的问题。知识检索解决缺少依据，记忆解决跨会话信息，任务拆分解决确实能独立处理或需要协作的工作。把它们全部接上，会增加需要调试的地方，并不能说明原来的错误已经解决。

每次改动提出一个可检查的判断，比如“提供候选设备能减少错误选择”。跑旧用例，也跑没有参与调优的新用例，再看错误是否减少。模型能自动生成更多请求，但样本需要核对，不能让它生成题目、解释答案，最后独自宣布系统变好了。

## AI 原生到底改变了什么？

> **面试官：你刚才讲的还是需求、测试和运维。AI 原生有什么不同？**

这些工作仍然需要做，变化在于谁执行，以及信息怎样交接。

Agent 可以检索资料、整理请求、实现代码、运行测试和分析日志。人可以把更多精力放在选择问题、确认约束、判断取舍和验收结果上。但任务交出去之前，要给足完成它需要的上下文，包括现有代码、接口约定、失败记录和可执行的检查。

比如让 Agent 优化刚才的家庭助手，我会先给它几条控制错设备的记录，要求解释错误来源，再提出最小修改并验证。它的工作范围和成功条件明确，就可以连续执行。我不需要在每一步手工操作，也不需要让它在缺少信息时不断猜测。

> **面试官：所以 AI 原生就是学会写更好的 Prompt？**

准确表达是其中一部分。更大的变化，是能把工作安排成可执行、可检查的过程。

有时适合明确分工：Agent 执行测试、整理失败，我根据证据决定是否扩大范围。有时需要来回协作：它发现两条需求冲突，我确认产品规则，它再继续实现。工作方式取决于任务，不必每次都由人拆到最细，也不能在关键条件不明时让它自己决定。

Ethan Mollick 用 Centaur 和 Cyborg 描述过这两种协作方式。他的研究还提醒人们，AI 的能力边界并不规则，看起来相近的任务可能表现不同。对工程项目来说，需要从自己的任务中发现边界；一项知识工作实验的提升比例，不能当作项目收益承诺。[^collaboration]

> **面试官：代码和测试都交给 AI，它们一起理解错了怎么办？**

这是需要单独防的情况。测试通过只能说明实现符合这些测试，不能说明测试表达了正确需求。

我会先从产品要求中固定关键验收条件，再让 Agent 实现。实现过程中保留这些条件，业务要求确实变了，再单独评审测试的调整。除了正常样本，还要用明确错误的样本检查测试是否真的会失败。测试需要能发现控制错设备、缺少授权和重复副作用，不能只断言工具返回了成功。

重要检查可以由另一段代码或独立评审完成，但换一个模型并不自动消除共同误解。遇到开放式质量判断，要用人工确认的样本校准评分器。Simon Willison 强调开发者需要确认生成的代码确实能工作；把运行过程自动化之后，这项验收责任仍然存在。[^coding]

> **面试官：那你还需要看代码吗？**

需要理解关键实现，尤其是控制真实副作用的地方。谁决定权限，哪里会发出控制请求，超时之后怎么处理，重启后从哪里恢复，这些必须能说清楚。

逐行手写可以交给 Agent，检查也可以自动执行。我需要知道检查依据来自哪里、覆盖了什么，发现问题时能定位到具体模块。高风险路径、难以撤销的改动和与预期不符的结果，需要更深入地读实现。

如果连“失败时会不会再次执行”都无法回答，就还缺少必要的验收依据。Agent 给出的说明也要和代码、测试和运行记录相互核对。

> **面试官：以后模型更强了，这套做法还需要吗？**

模型变强，可以让更多任务直接完成，也可能减少为了补足能力而增加的步骤。旧模型需要很长的提示或多个 Agent，新模型能用简单流程完成，就应该用同一组任务验证后简化。

但是用户目标、权限和外部状态不会由模型版本自动定义。测试旧知识是否还适用，记录动作实际有没有发生，判断这个版本能不能发布，仍然是项目本身的工作。

我希望一次改动能够回答几个具体问题：哪些用户任务变好了，哪些变差了，每次成功需要多少时间和成本，发生异常后该怎么处理。模型继续升级时，有这些依据，才能及时用上新能力，也知道哪些原有步骤可以删掉。
