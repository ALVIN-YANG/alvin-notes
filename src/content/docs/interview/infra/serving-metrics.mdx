TTFT 是发送请求到收到首个输出 token 的时间。ITL 是相邻输出 token 的间隔。TPOT 通常指首个 token 之后的平均每 token 时间。端到端延迟则从请求发出算到最后一个输出，受到输出长度影响。

总 token/s 表示系统单位时间完成多少工作，不代表单个用户生成得快。批量加大后，总吞吐可能上升，排队和逐字等待也可能一起上升。

<InterviewVisual src="/images/interview/cards/infra-serving-metrics.webp" alt="指标与有效压测图解。t0 发送；t1 首 Token；t2 下个 Token；tn 最后 Token；TTFT = t1 − t0；ITL = t2 − t1；E2E = tn − t0；TPOT = (tn − t1)/(n − 1)，n > 1；吞吐 ≠ 单请求速度；P99 ≠ 平均；流事件 ≠ Token；固定负载、口径与成功条件。" />

输出数大于 1、首尾 Token 的时点可观测时，`TPOT = (最后一个 Token 的时间 - 第一个 Token 的时间)/(输出 Token 数 - 1)`。只输出一个 Token 时，该公式没有定义，应标记不适用；若平台约定记为 0，也要说明统计口径，不能把这个 0 解释为真实测得的生成间隔。

一个流式事件可能包含多个 Token，也可能只有角色、工具参数或结束标记。事件到达间隔不能直接当作 ITL；按事件数计算平均值，也不是按 Token 数计算的 TPOT。比较指标前，要对齐客户端或服务端的测量位置、输出 Token 计数和分包方式。

## 压测时固定哪些条件

固定模型版本、精度、硬件、输入输出长度分布、请求到达节奏和缓存条件。冷热缓存、重复 Prompt 分开报告；输入和输出 token/s 也分开报告。

固定并发的闭环压测会在服务变慢时自动降低发送速度，可能看不出持续到达的流量造成多少积压。按固定到达率发送请求，更容易观察排队，但要设置超时、拒绝和停止条件。

### P99 可以从平均值推出来吗？

不能。P99 是 99 百分位，平均值无法反映长尾。各实例的 P99 也不能直接平均成全局 P99，应从一致口径的样本或可合并分布中计算。

### 什么叫有效吞吐？

先定义成功条件，例如内容完整、没有超时，TTFT 和输出间隔都达标，再统计这些请求每秒完成多少，或生成多少 token。只报吞吐而不报成功率和延迟约束，容易掩盖过载。
