Prefill 处理输入 token，建立 KV cache，并产生用于生成首个输出 token 的结果。Decode 利用已有缓存计算新位置，逐步生成后续 token。

长 Prompt 要做更多 Prefill 工作，可能让首字等待变长。首字出来后每个 token 的速度，是另一个问题。所以要分开看 TTFT 和后续输出间隔。

```mermaid
flowchart LR
  A[发送请求] --> B[网络、排队与输入处理]
  B --> C["Prefill<br/>处理输入并建 KV"]
  C --> D[首个输出 token]
  D --> E[Decode 新位置]
  E --> F[下一个 token]
  F --> E
```

## 从慢的阶段找原因

输入变长、输出长度不变，先看 Prefill 工作量；输入不变、流量升高，先看排队；逐字输出变慢，则查 Decode 批量、上下文长度、KV 容量和带宽，也要看长 Prefill 是否挤占执行时间。

较大批量的 Prefill 往往更受计算能力限制，小批量 Decode 常受权重和 KV 读取带宽限制。模型、硬件、上下文和批量都会改变瓶颈，仍要测。

### 前缀缓存能加速哪一段？

命中后可以复用已计算前缀的 KV，减少 Prefill。它不是回答缓存，也不保证后续生成都变快。跨实例复用还要计算数据传输的开销。

### 流式输出会让模型算得更快吗？

流式传输让用户更早看到已生成的结果，本身不减少模型计算。客户端要观测首个 Token 和后续输出的到达时间，需要流式返回；非流式响应只能直接测到整次请求耗时。服务端仍可通过埋点记录首个 Token 和后续生成时间，但这些指标不包含完整的客户端网络等待，不能与客户端口径直接混用。
