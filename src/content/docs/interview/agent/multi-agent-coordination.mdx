任务能拆成相对独立的工作，或需要不同工具和权限时，多 Agent 才容易产生收益。如果所有步骤都依赖同一份上下文、必须串行完成，增加 Agent 往往只增加消息、成本和协调难度。

例如调研三家供应商，可以分别收集材料，由一个负责人核对并合并。每个子任务说明范围、来源要求和完成条件；合并者要核实证据，不能把三个自然语言结论拼起来就算完成。

## 交接的是任务，不是全部聊天记录

交接包保留目标、已有证据、约束、下一步和完成条件，避免把大量无关历史塞给接手者。任务状态和负责人要有明确记录，消息送达不等于任务被接手，更不等于完成。

多个 Agent 不应同时修改同一资源而没有协调。可以指定唯一写入者，让其他 Agent 返回建议；确实要并发写时，用业务事务或版本检查处理冲突。模型协商不能代替并发控制。

### 并发后延迟和成本怎样变化？

独立任务并发时，完成时间可能接近最慢的子任务再加合并时间。总调用量通常仍是各任务之和，还可能多出沟通和复核。比较单 Agent 基线的成功率、成本和尾延迟，才能判断是否值得拆。

### 子 Agent 卡住了怎么办？

设置截止时间、明确状态和失败原因。负责人可以重派或降级，但要确认旧执行者不会继续写入同一资源。限制交接次数，避免 A 交给 B、B 又交给 A 的循环。
