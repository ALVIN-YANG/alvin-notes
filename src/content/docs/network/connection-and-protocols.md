一次网络调用的可靠性、延迟和安全性，几乎由协议栈的几个关键选择决定：传输层选 TCP 还是 UDP，连接复用还是用完即关，加密在握手哪一步完成，应用层用 HTTP 还是 RPC。这些选择彼此耦合——HTTP/3 换用 QUIC，是因为 TCP 队头阻塞在内核里改不动；MQTT 进物联网，是因为一问一答配不上弱网省电的设备。理解每个协议解决了什么、把代价转嫁给了谁，比记住报文格式更有用。

## 1. TCP、UDP、KCP 与 Socket：传输层怎么选

TCP 与 UDP 的差异可压缩成四个维度：TCP 面向连接（先握手再传输，双方维护连接状态），提供确认、重传、排序的可靠传输，带流量与拥塞控制，头部较大且以字节流交付——字节流没有消息边界，接收方要自己拆包，这正是粘包问题的根源；UDP 无连接、不确认不重传，头部只有 8 字节，以独立数据报交付、天然保留边界。

但“UDP 更快”并不成立：UDP 大包靠 IP 层分片，丢一片要重传整包，早期 NFS 就吃过亏。许多应用会按需在 UDP 上补充可靠性——KCP 是典型：UDP 之上的应用层可靠逻辑，用更小的重传超时、可调阈值的快速重传和可关闭的拥塞控制，多耗带宽换更低延迟；QUIC 走同一条路，只是做到了传输层的完整度。

Socket 不是协议，是操作系统封装 TCP/UDP 后暴露给程序的编程接口：服务端创建、绑定、监听、接受连接，客户端创建后发起连接，之后收发、关闭。一条 TCP 连接由四元组（源 IP、源端口、目的 IP、目的端口）唯一标识，端口 0–65535，其中 0–1023 为知名端口；DNS 是少数同时使用 TCP 与 UDP 53 端口的协议。IPv6 没有 ARP，地址解析由 NDP（邻居发现协议）承担。

选型只有一条主线：不能容忍错误和乱序（网页、文件、支付）选可靠传输；不能容忍卡顿（语音、直播、游戏）允许丢包换实时。

## 2. TCP 连接生命周期：握手、序号与关闭

三次握手的本质是双向确认收发能力并同步初始序列号：客户端发 SYN（SEQ=x）进入 SYN_SENT，服务端从 LISTEN 收到后回 SYN+ACK（SEQ=y，ACK=x+1）进入 SYN_RCVD，客户端再回 ACK（y+1），双方进入 ESTABLISHED。两次不行：延迟到达的旧 SYN 会让服务端为客户端早已放弃的连接分配资源空等，耗尽连接表；四次多余：服务端的 SYN 与 ACK 可合并在一个报文里，多一次只增加延迟。

可靠性靠一套组合拳：每个字节有序号、报文头标注首字节序号，接收方排序去重；ACK 是累积确认——ACK n 表示 n 之前的字节全部收到；每段数据启动重传计时器，超时未确认即重发；收到 3 个重复 ACK 立即快速重传，不必等超时；普通 ACK 说不出“后面哪些已收到”，SACK 在选项里携带已收到的不连续块，让发送方只补真正丢失的部分；校验和发现损坏直接丢弃、不回 ACK，交由重传兜底。

关闭用四次挥手：主动方发 FIN，对方 ACK，对方数据发完再发自己的 FIN，主动方 ACK 后进入 TIME_WAIT 等待两倍 MSL，保证最后一个 ACK 丢失时对方能重发 FIN。TIME_WAIT 堆积是高频短连接场景的容量问题。

## 3. 流量控制与拥塞控制：保护接收方，也保护网络

流量控制保护的是接收方：应用读得慢，内核缓冲区就会溢出丢包。接收方在每个 ACK 携带接收窗口（缓冲区剩余空间），发送窗口随 ACK 右滑，分已确认、已发未确认、可发送、不可发送四区。缓冲区满时通告零窗口，发送方停发并用持续计时器定期探测，防止窗口更新丢失造成互等死锁。应用每次只读几字节会导致通告小窗口、网络塞满小包（糊涂窗口综合症），解法是接收方攒够空间再通告、发送方凑够数据再发（Clark 与 Nagle 的思想）。

拥塞控制保护中间网络：路由器缓冲区填满就开始丢包。发送方维护拥塞窗口，与接收窗口取小作为实际发送上限。Reno 是丢包驱动：慢启动指数增长、到阈值后线性增长，丢包触发快重传快恢复、窗口减半——简单稳定，但高带宽下一次随机丢包就减半，浪费严重。CUBIC 是 Linux 默认拥塞算法，记录丢包时的最大窗口 Wmax，用三次函数先平缓逼近、再加速越过，更适配高带宽长距离链路，但仍是丢包驱动，遇无线随机丢包照样误降速。BBR 是模型驱动：丢包只触发重传、不参与速率决策，靠持续采样瓶颈带宽和最小 RTT 建模，经 Startup、Drain、ProbeBW、ProbeRTT 四阶段运行，在 Wi-Fi 和 4G/5G 等随机丢包链路上表现更好；短板是与 CUBIC 等丢包驱动流共存时的公平性，以及带宽探测带来的瞬时排队波动。实践上，有线数据中心常用 CUBIC，无线移动场景倾向 BBR——平衡的都是带宽利用率、排队延迟与丢包。

## 4. 连接管理的工程现实：长短连接、Keepalive、超时与 RST

短连接一次请求一条连接、用完四次挥手；长连接建一次复用多次，靠连接池统一管理。TCP 并不必然每个请求都关连接——HTTP/1.1 起持久连接就是默认行为。长连接的代价是四个坑：空闲连接被防火墙或 NAT 清掉会话表后，复用时收到 RST；连接泄漏耗尽文件句柄；服务端重启后客户端残留死连接；心跳太频繁浪费带宽、太慢剔不出死连接。注意 NAT 会改写地址和端口，响应路径也不保证对称，中间设备的连接状态比端点脆弱得多。

Keepalive 有两层，别混淆：TCP Keepalive 是内核级探测（Linux 默认空闲约 7200 秒才开始探），判断对端是否还活着；HTTP Keep-Alive 是应用层连接复用。拔了网线 TCP 不会立刻报错——没有报文交互就没有失败信号，只能靠重传超时或 keepalive 在数十秒到数小时后发现。超时要分两类配：连接超时管建连阶段（SYN 发出后等待应答），读写超时管已建立连接上的单次收发，且都应小于链路上中间设备的空闲清理时间，否则永远在复用一条已被静默回收的连接。

RST 是强制断连，连接上的数据可能被直接丢弃。三个最常见成因：访问没有进程监听的端口；空闲连接被中间设备清理后再发数据；服务端重启丢失连接状态。服务只监听 127.0.0.1 时，外部访问同样被 RST 拒绝而本机自测正常，部署后先确认监听地址。排查先抓包确定 RST 是谁发的，再决定查进程、中间设备超时还是代码，不要先动业务代码。

服务器能扛多少连接？65535 限制的是单客户端对单一目标的源端口数，不是服务器连接上限——一个端口可服务大量四元组不同的连接。真实瓶颈是文件描述符上限、每连接内存（内核缓冲区粗略 KB 级）、CPU 收发包能力和内核参数；默认几千连接，配合 epoll 和调优可到百万级（C10M）。注意 listen 的 backlog 队列满时，新 SYN 可能被直接丢弃，客户端表现为连接超时而非拒绝，压测中的“莫名超时”常源于此。

## 5. HTTPS 与 TLS 1.3：把不可信信道变成可信信道

HTTPS = HTTP over TLS，设计被一连串攻击倒逼出来：对称加密快，但密钥也要经不可信信道分发，形成死结；非对称加密让公钥可以公开，但慢且只能解决单向问题，于是有了混合加密——用非对称手段护送对称会话密钥，之后全走对称加密。公钥仍可能被中间人调包且双方无感，于是引入 CA：用私钥对服务器公钥信息签名形成数字证书，浏览器用预置根证书沿证书链验签，伪造者盖不出 CA 的章。

“用服务器公钥加密预主密钥”的 RSA 密钥交换是演进史上的经典模型，不是现行流程。为兼容中间设备，ClientHello 的 legacy_version 字段仍写 1.2，真实版本由 supported_versions 扩展协商；在此之上 TLS 1.3（RFC 8446）做了三件事：瘦身——移除 RC4、DES、CBC 模式、MD5/SHA-1 和 RSA 静态密钥交换，只保留加密与完整性合一的 AEAD 套件；提速——密钥协商材料随 ClientHello 携带，握手压缩到 1-RTT，ServerHello 之后全部加密；安全——密钥交换统一走 ECDHE 临时密钥（推荐 X25519），每次会话独立，拿到长期私钥也无法解密历史流量，即前向安全。会话密钥由 HKDF 从多个随机源派生。恢复会话可用 PSK 实现 0-RTT——不是不握手，而是握手同时携带 early data——但其数据可被重放，只应用于幂等请求，并配合时间戳或随机数校验。

## 6. HTTP：报文、状态码、身份认证与 HTTP/3

HTTP 的模型是一问一答：请求报文由请求行（方法+路径+版本）、请求头和可选请求体组成，响应报文由状态行、响应头和响应体组成。方法表示动作、路径表示对象、状态码表示结果。状态码五类：1xx 信息（100 Continue）；2xx 成功（200、204 无返回体、206 分片内容）；3xx 重定向（301 永久、可能被缓存，302 临时、304 是缓存协商而非跳转）；4xx 是请求方问题（400 参数错、403 无权限、404 不存在、405 方法不允许、429 限流）；5xx 是服务端问题——记住 500 内部错误、502 网关拿到无效响应、503 过载、504 网关超时；排障按 4xx 查请求、5xx 查后端划分责任。一个网页背后是 HTML 加 CSS、JS、图片的多次请求响应。

HTTP 无状态，身份认证是补出来的。Cookie 让浏览器自动保存并携带登录标记，应配合签名防篡改，并设置 HttpOnly、Secure、SameSite 缓解 XSS 与 CSRF。Session 把数据挪到服务端、浏览器只存 Session ID，但分布式部署下请求被负载均衡打到别的机器就“掉登录”，常规解法是用 Redis 做中心化存储，但需考虑其可用性与性能瓶颈。移动端没有浏览器的自动携带机制，于是有了由客户端手动维护的 Token；JWT（RFC 7519）是 Token 的标准化：Header、Payload、Signature 三段，服务器重算签名即可校验，无需查会话存储，实现无状态——注意 Payload 只签名不加密，敏感数据不能放进去，且签发后难吊销，靠短过期加刷新弥补。

协议演进围绕连接效率：HTTP/1.1 引入持久连接，但请求串行、有应用层队头阻塞，浏览器只好对每个域名并行开多条连接——“每域名约 6 条”是实现策略而非协议规定，pipelining 因响应须按序返回而名存实亡。HTTP/2（RFC 9113，源自 SPDY）改用二进制帧，同一连接内的多个流交错传输，多路复用解决了 HTTP 层队头阻塞，配合 HPACK 头部压缩；服务器推送因浪费带宽而少有浏览器启用。但 TCP 层队头阻塞仍在：一个丢包卡住所有流，而 TCP 在内核里改不动、升级慢，弱网还容易把随机丢包误判为拥塞。QUIC（RFC 9000/9001）因此在用户态基于 UDP 重写可靠传输：传输握手与 TLS 1.3 合并为 1-RTT、可 0-RTT 恢复；流之间相互独立，单流丢包不阻塞其他流，消除 TCP 层队头阻塞；用连接 ID 标识连接，Wi-Fi 切蜂窝、IP 变了连接也不断。HTTP/3 就是跑在 QUIC 上的 HTTP，工程上不要唯版本论，应优先 HTTP/3、链路不通时自动降级到 HTTP/2 或 1.1。另一个补丁是 HTTPDNS：传统 DNS 走 UDP 53 明文查询，易被劫持且调度粗糙；App 通过 HTTP/HTTPS 接口直接向服务商解析，可防劫持、按出口 IP 就近返回列表自行择优，适合对解析可控性要求高的移动端。

## 7. RPC、gRPC、WebSocket 与 MQTT：应用协议的四种分工

RPC 是一种思路而非具体协议：像调用本地函数一样调用远端服务。微服务内部常用 RPC 框架，与 HTTP 的差异在服务发现（注册中心而非 DNS）、连接管理（长连接池）和序列化（Protobuf 比 JSON 紧凑）；gRPC 是其中事实标准之一：HTTP/2 承载、Protobuf 编码，支持一元、服务端流、客户端流和双向流四种调用模式。对外接口仍普遍用 HTTP——生态、调试和网关都成熟。

WebSocket 补的是 HTTP 无法服务端主动推送的短板：握手复用 HTTP——请求头带 Upgrade: websocket，服务端回 101 Switching Protocols 后同一 TCP 连接切换为全双工轻量帧通道，配 Ping/Pong 心跳防中间设备清空闲连接。聊天、弹幕、行情、协同编辑用它；没有实时需求就不必承担连接管理成本。

MQTT 为物联网而生：发布订阅模式，设备只连 Broker、按 Topic 收发，彼此解耦；固定头部最小 2 字节，省电省流量；内置三档 QoS（0 最多一次、1 至少一次、2 恰好一次）、断线重连、遗嘱消息（设备异常掉线由 Broker 代发通知）和持久会话（离线期间消息暂存补发）。HTTP 永远客户端先开口、每次带完整头部，服务器下发指令只能轮询，在弱网、低算力、海量设备场景结构性吃亏——不是 HTTP 不好，是它的岗位在服务人而非设备。

## 8. 流媒体与实时传输：RTMP、RTP/RTSP、HLS 与 WebRTC

直播链路分推流与分发两段。推流主流是 RTMP：跑在 TCP 上、默认 1935 端口，流程为 TCP 握手、RTMP 握手（C0–C2/S0–S2 同步版本与时间戳）、connect 建逻辑连接（RTMP 消息不自描述，必须先建立会话上下文）、createStream 申请流、publish 带流名开始推；消息切成默认 128 字节的 chunk 交错发送，头部在 chunk 间复用。端到端延迟经验量级 1–3 秒。

拉流分发两条路：HTTP-FLV 与 RTMP 同为 1–3 秒量级、明显低于 HLS，但依赖播放器支持；HLS 把流切成 TS 分片加 M3U8 索引，普通 Web 服务器和 CDN 就能承载、苹果设备原生支持，代价是延迟常见 5–30 秒，二级索引支持多码率自适应。注意协议延迟不等于端到端延迟，采集、转码、分发各段都在叠加。

监控与 IPTV 场景是 RTSP+RTP 的组合：RTSP 是遥控器，只传播放、暂停、关闭等信令，丢不起，走 TCP；RTP 打包传输音视频，靠序列号抗乱序、时间戳做音画同步、SSRC 区分流，配套 RTCP 只监测丢包率不补救。RTP 通常跑 UDP 换低延迟——画面丢了等下一帧，比 TCP 重传卡住后续画面划算——也有 RTP over TCP（与 RTSP 信令交织）的变通，用延迟换 NAT 穿透与防火墙通过率。WebRTC 则是浏览器原生的点对点实时通信技术栈：媒体采集编码、信令协商（走 HTTP/WebSocket）、STUN/ICE/TURN 穿透 NAT，优先直连、失败走 TURN 中继，媒体走 SRTP（通常基于 UDP），端到端延迟可到 1 秒内，用于会议、连麦、云游戏；大规模分发仍需媒体服务器转发。

## 9. 微服务、容器与负载均衡：把协议跑在生产环境

微服务把单体应用拆成独立部署、独立扩容的服务，服务间用 RPC 或 HTTP 通信，靠注册中心做服务发现；换来发布与扩缩容灵活，付出分布式系统的全部复杂度——超时、重试、熔断和链路追踪成为必修课。Docker 用 namespace 和 cgroups 把应用连同依赖打包成容器，抹平环境差异；Kubernetes 在其上编排：Pod 是最小调度单元，Service 提供稳定入口，控制器负责调度、扩缩容与故障自愈；跨节点容器网络依赖 CNI 的 Overlay 或路由方案。

流量进门要经过负载均衡。四层负载均衡只看 IP 和端口转发，性能高、不解析应用内容；LVS 是 Linux 上的代表，通过内核 IPVS 工作，常见模式有 NAT（改写地址、进出都过调度器）、DR（直接路由，只改 MAC、响应由后端直接回客户端，吞吐最高但要求同网段）、TUN（IP 隧道跨网段）和 FULLNAT（同改源和目的地址，牺牲性能换部署自由）。七层负载均衡（Nginx、Envoy 等）终止 TLS、解析 HTTP，能按路径、域名、Header 路由，做灰度和限流，代价是每个请求都走完应用层处理。实践里两者分层配合：大流量入口用四层扛连接，业务路由交给七层，健康检查与会话保持要对齐上文的 Keepalive 与超时配置——中间层清了连接而端点不知道，就是线上 RST 的经典来源。

从 Socket 到负载均衡，每个协议都是取舍：可靠性换延迟、状态换简单、灵活换开销。选型没有“越新越好”——HTTP/3 要配降级链，长连接要配心跳和超时，0-RTT 要限制幂等。先排定业务对延迟、可靠性和运维成本的优先级，再让协议去匹配，是这套知识最能落地的用法。
